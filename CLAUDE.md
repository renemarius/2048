# CLAUDE.md — 2048 Hangul Conjugation

Reference for Claude Code when working in this project. `constitution.md`
in this folder is the source of truth for product/scope decisions — read it
before proposing features or architecture changes. This file is about *how*
to work here, not *what* to build.

## Spec-driven workflow

- `constitution.md` holds the vision, principles, and the versioned
  checklist (v1/v2/v3...). Treat unchecked boxes as the backlog and checked
  boxes as validated-done.
- Before starting work on an item, confirm which checklist item it maps to.
  Don't implement v2+ items while v1 boxes are still unchecked (Principle 5:
  ship the loop before the polish) unless the user explicitly asks to jump
  ahead.
- When a checklist item is genuinely done *and verified working* (not just
  code written — actually run/tested), check it off in `constitution.md` in
  the same session, and say so.
- If implementation reveals a decision the constitution left `OPEN` or
  didn't anticipate, resolve it with the user and update the relevant
  section of `constitution.md` rather than silently deciding and moving on
  — this doc needs to stay accurate as the plan evolves.
- Future feature work that needs more detail than the constitution carries
  (e.g. a full v2 grammar-engine spec) should live in `specs/` as its own
  doc, linked from the constitution — don't bloat the constitution itself
  with implementation-level detail.

## Repo / git

- This folder is its own git repo (initialized here directly — `git
  rev-parse --show-toplevel` resolves to this folder, not the user's home
  directory). `git add -A` / `git commit` scoped to this repo are safe.
  Remote: `origin` → `github.com/renemarius/2048` (`main` branch). Pushes
  are a user action — confirm before pushing, don't push on your own
  initiative just because a commit was made.
- **Commit after each feature is built and verified working** — not on
  any other cadence (not every small edit, not batched at session end,
  not only when asked). A completed, checked-off checklist item is a
  natural commit boundary. This was an explicit standing instruction from
  the user, not a one-off.
- `next dev` refuses to start a second server for the same project and
  instead prints the already-running server's URL/PID (it writes a lock
  file at `apps/web/.next/dev/lock`). If one is already running, query
  that one (`curl`, check `apps/web/.next/dev/logs/next-development.log`)
  rather than starting a duplicate or killing the user's session.
- `apps/web/AGENTS.md` and `apps/web/CLAUDE.md` are auto-generated by
  `next dev` (Next.js 16.3+, version-matched framework docs for agents —
  see `node_modules/next/dist/docs/`). This is intentional upstream
  behavior, safe to keep/commit, and does not touch this root `CLAUDE.md`.

## Architecture (per constitution.md Section 5)

- `packages/core/` — framework-agnostic TypeScript. Board state, merge
  rules, the conjugation engine, scoring/dictionary logic. No React, no
  Next.js, no DOM APIs. This is what a future mobile app reuses — keep it
  that way.
- `apps/web/` — Next.js (App Router) + TypeScript + React, deployed on
  Vercel. Imports `packages/core`; owns rendering, input handling, and
  `localStorage` persistence.
- The conjugation engine is the correctness-critical part of this project
  (constitution Principle 1). It should have unit tests covering every word
  in the v1 vocab list × every supported ending, not just happy-path
  examples.

## Verification (no browser tool in this environment)

As of this session, there is no browser automation available (Chrome
extension declined by the user — they can revisit with `/chrome`; check
whether that's changed before assuming it's still unavailable). Until it
is, the established verification bar, in order, before calling a feature
done:

1. `npm run test` (packages/core) — the real correctness bar per
   Principle 1. Every pattern-group/mechanic gets exhaustive tests, not
   spot checks.
2. `npm run typecheck` and `npm run build` (root scripts, cover both
   workspaces) — must be clean.
3. Boot `next dev` (check for an already-running server first — see
   above) and confirm it compiles/serves with no errors in the log.
4. When a bug is reported from the user's own manual testing, reproduce
   the exact scenario as a regression test before fixing it, not just a
   general-purpose test (e.g. the duplicate-stem/ending-pileup fix added
   tests that recreate the exact screenshot scenario).
5. Explicitly tell the user what could *not* be verified this way
   (visual rendering, animation timing, real keyboard/click interaction)
   rather than implying it was — and ask them to do a hands-on pass.

## Conventions

- TypeScript strict mode.
- No comments explaining *what* code does; only for non-obvious *why*
  (e.g. a specific Korean vowel-harmony rule or an irregular-class
  exception) — same bar as normal.
- Keep UI styling swappable rather than hard-coded, since theming is a
  named v3 feature — don't block that future work with one-off inline
  styles that assume a single look.
